FreeToken · 排障报告

Qwen3.8-27B-NVFP4-FTW 输出乱码 · 根因定位

RTX 3090（sm_86）× Windows × FreeToken 0.1.2+g141c31a8d  ·  2026-09-12
结论

转换和模型都没有问题，问题在引擎侧：FreeToken 在这台 sm_86 / Windows 机器上跑不通这个模型。

模型能加载、能起服务、出词速度正常（~17 tok/s），但从第 1 个 token 起 logits 就是乱的， 并且会随机死锁。本机没有第二个 attention 后端可切换，因此无法再往下二分，也无法修复。

一、症状（干净服务上稳定复现）

请求耗时completion_tokens返回 text
temperature=0（贪心 → torch.argmax） 0.4 s7 "" 空串
temperature=1.0, top_k=20, top_p=0.95 0.4 s7 샘··샘中新网····alisierte 乱码
同样参数再跑一次（max_tokens=3） 挂死 > 180 s，ft ctl stats 显示 active=1 不下降 死锁

同一参数下既可能秒回、也可能永久挂起 —— 非确定性。杀掉客户端也不自愈，只能重启服务。

二、「空串」的真相：不是没出词，是出的全是乱码 token

OpenAI 接口拿不到 token id（echo / logprobs / return_token_ids 都被拒）， 改走引擎的离线 API freetoken.llm.LLM 后才看到真实 id：

tokenizer/detokenize.py 里：文本以 \ufffd 结尾且不含空格时， find_printable_text() 返回 ""，于是全部输出被丢弃。

乱码 token 是跨语种 + 代码标识符的大杂烩（sourceMapping、:UIControl、 ImplOptions、PENDAHUL、aliaierte、稿件来源、애니、ジオ）—— 典型的 logits 全乱特征。健康的模型对 "The capital of France is" 的贪心下一个 token 应该是 " Paris" 级别。

四、剩余嫌疑人

做完上面 13 项后，还可能出错、但本机无法再进一步二分的只剩：

  • triton paged-attention 后端（16 层全注意力）—— kernel/triton/attention.py 的 extend_paged_attention / decode_paged_attention。 这是唯一没被覆盖的大 kernel。
  • 少数未被参考实现对冲的 norm kernel（q/k RMSNorm 的批量路径等）。
  • 模型层间接线（残差 / 位置 id / 最终 norm）—— 与 HF 逐层对齐需要一份可跑的 HF 参考前向， 24 GB 显存放不下 27B 的 bf16 反量化版本，此路不通。

要定位到具体哪一行代码，需要厂商在 sm_86 上跑同一份 FTW 权重做对照。

五、建议的下一步路线

① 用 llama.cpp + GGUF（最稳）

G:\AI\ 下已有 Qwen3.8-27B-BF16-SSMFIX-UD-Q3_K_XL.gguf 等多个 GGUF， llama.cpp 也已下载（llama-b10679-bin-win-cuda-12.4-x64.zip、LammacppStart）。 GGUF 对混合 SSM/GDN 模型的支持路径与 FreeToken 完全不同，是绕开本次问题的直接办法。

② 改用 W4A16 量化再喂 FreeToken

G:\AI\Qwen3.8-27B-int4-AutoRound 是 W4A16（int4 权重 + bf16 激活）。 W4A16 在 sm_86 上不依赖 FP4 硬件路径，比本次的 W4A4 NVFP4 回退链可靠得多。

③ 反馈上游

厂商验证配置是 Linux + 4×GB300 + TP=4；Windows + sm_86 + TP=1 属未验证路径。 把本报告的复现步骤与 token id 样本一起提给 FreeToken 团队，定位成本最低。

④ 不建议做的事

继续调 --memory-ratio / --cache-type / --page-size / 温度等参数。这些都已经验证过，改不动这个问题 —— 那是「参数没调好」和「内核算错」的区别。
