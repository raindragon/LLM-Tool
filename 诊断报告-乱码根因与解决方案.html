输出乱码 · 根因判定与解决方案

Qwen3.8-27B-NVFP4 → FTW 转换 · FreeToken 引擎 · RTX 3090 (sm_86) · Windows  |  诊断完成时间 2026-09-12 19:4x

结论：不是参数问题，也不是转换问题 —— 是引擎在这块卡上跑不动这个检查点

权重完全正确（已逐元素对拍验证），模型和显卡也都没问题（同一张 3090 用 llama.cpp 跑同一模型，输出完全正常）。乱码来自 FreeToken 在 sm_86 上模拟 FP8 / FP4 计算 + 为加载该检查点手工改过的 7 个内核胶水文件。

这个检查点是 NVIDIA Blackwell 专用（官方原话：produced and validated on GB300， 仅支持 SGLang，首选 Linux）。RTX 3090 是 Ampere，既没有 FP8 张量核、也没有 FP4 张量核， 两种格式都得靠软件模拟 —— 官方包甚至不认这套检查点，是手工改了 7 个文件才勉强加载起来的。

把 FTW 里的张量读出来，和原始 safetensors 按 ModelOpt 的公式反量化后逐元素比较。 脚本：verify_ftw_weights.py / verify_ftw_weights2.py。

四、为什么这块卡跑不了

  • 检查点是 Blackwell 专用。RadixArk 官方 README 明确写：算力兼容性 “NVIDIA Blackwell（本检查点在 GB300 上产出并验证）”，运行时仅支持 SGLang，首选 Linux。 它是 混合精度 NVFP4：MLP + lm_head 是 NVFP4 W4A4（权重和激活都是 4 bit）， 注意力是 FP8 W8A8，KV cache 也是 FP8。
  • RTX 3090 是 sm_86（Ampere）。Ampere 有 BF16 / INT8 张量核， 但没有 FP8 张量核（Hopper 起才有）、更没有 FP4 张量核（Blackwell 才有）。 两者都必须用软件模拟。W4A4 还需要把激活也压到 4 bit，在 Ampere 上只能靠整数运算硬凑。
  • 官方包根本不认这套检查点。安装包里有 7 个文件被手工改过 （用安装记录的 SHA256 比对出来的）： layers/base.py、models/quant_linear.py、 models/qwen3_5_moe/ 下的 __init__.py · config.py · gdn.py · model.py · moe.py；另外还有个手写的 weight_int4.py 直接顶替了官方编译版权重读取器。这些改动是「能让它加载起来」的原因， 也是剩下最可疑的一环 —— 但除此之外已经没有可调的开关了。
  • 这不是调参能解决的。权重对、内核各自单元测试对、参考实现也救不回来 —— 说明误差产生在多算子协同或模拟精度累积上，属于引擎在非目标硬件上的路径缺陷， 需要厂商修，不是使用者能绕过的。

五、解决方案

方案 A · 推荐

用 llama.cpp 跑 GGUF（已验证可用）

本机已有现成的 llama.cpp 和 4 个 GGUF，同卡实测 41 t/s、输出正确。这是当前唯一能立刻拿到正确结果的路径。

# 直接对话（一次性）
llama-cli.exe ^
  -m "G:\AI\Qwen3.8-27B-BF16-SSMFIX-UD-Q3_K_XL.gguf" ^
  -ngl 99 -c 32768 --flash-attn on --temp 0.7

# 或起服务，用 OpenAI 兼容接口
# 现成脚本：G:\AI\llama-turboquant-windows\start-server.bat

代价：GGUF 是另一次量化，和 NVFP4 不是同一份权重（精度约 IQ3_S/IQ4_XS 级别）。

方案 B · 可选

换一个 Ampere 能跑的量化格式给 FreeToken

本机还有 Qwen3.8-27B-int4-AutoRound（纯 W4A16 int4， 无 FP8/FP4 激活量化）。这个格式正好是手写读取器最初支持的，理论上不吃 FP4 模拟的亏。 需要先转 FTW 再试，结果不保证。

ft.exe checkpoint \
  --model-path G:\AI\Qwen3.8-27B-int4-AutoRound \
  --output-path G:\AI\Qwen3.8-27B-int4-FTW

保留 FreeToken 的速度优势，但需要一次转换 + 一次验证。

方案 C · 不建议

继续挖 FreeToken 的 sm_86 模拟缺陷

剩下的可疑面是 7 个手改文件 + 16 层 paged-attention 的 triton 后端。没有可替换的注意力后端可装（flashinfer / vLLM 在 Windows + sm_86 上都不可用）， 只能靠逐层对拍激活值硬啃，工作量大且不保证有解。

六、本次新增的可复用脚本

脚本用途
probe_quality.py 对运行中的实例发确定性贪心请求，判断输出是否连贯。支持 --launch 自行起服务、--env 注入环境变量、 --arg 追加 ft 参数，服务日志落盘到 probe_server.log

关键结论：FTW 转换产物正确、可保留；乱码由引擎在 sm_86 上的 FP8/FP4 模拟路径导致。
