### FreeToken 起不来的真正原因：preflight 的"安全余量"卡太死

目标模型 `G:\AI\Qwen3.8-27B-NVFP4-FTW`：**权重 18.78 GiB**（3 个 .ftw：7.99 + 7.96 + 2.83），空闲显存 **22.7 GiB**，48 层线性注意力（GDN），单请求状态池 0.143 GiB。

上一轮为了修 OOM 把预留提到 `max(3.5 GiB, 15%)`、ratio 上限压到 0.90 → `可用池 = 0.846×22.7 − 18.78 = 0.41 GiB`，再减 GDN 状态池，KV 必为负 → `recommended=None` → 判死。**安全档对这类"差一点点"的模型是误杀。**

修法：`preflight()` 改成**两档**（`server.py` + `launch_model.py` 同步）：
- `safe`：预留 max(3.5 GiB, 15%)，ratio ≤ 0.90

- 先试 safe，全不满足退 aggressive；返回体加 `tier` 字段，前端显示「极限档（能跑，但可能 OOM）」徽章。

对该模型的最终方案：`ratio 0.934 · 并发 4 · naive · prefill 4096 · cuda-graph-max-bs 1`，KV 余量 1.69 GiB。

## 第五轮：显卡识别的**真正根因**（前面几轮都判错了）

前几轮我把「显卡识别不到」归因为浏览器缓存/并发撞车 —— **都不是根因**，只是表象。这轮直接问用户正在运行的进程要数据，才定位准。

### 决定性证据

直接请求用户进程 `http://127.0.0.1:8420`：`/api/env`、`/api/sysinfo`、`/api/gpu` **三个接口 gpus 全是空**，
且 `/api/preflight` 返回 `freeGB = 0.0`（读不到显存 → 连带 FreeToken 被判「装不下」而起不来）。
同时判别接口是否为最新代码：`tier` 字段存在 + `/api/serve/last-log`、`/api/fs/scan?mode=gguf` 都 200 → **代码是新的，但后端真的读不到显卡**。

`/api/env` 的 `python` 字段给出答案：**`3.11.9`**。

### 根因：`py -3` 指向 32 位 Python，System32 被 WOW64 重定向

```
py -3  ->  C:\Users\zymzy\AppData\Local\Programs\Python\Python311-32\python.exe
           3.11.9 (MSC v.1938 32 bit (Intel))
```

32 位进程访问 `C:\Windows\System32` 会被 WOW64 **静默重定向到 `SysWOW64`**，而驱动只在 64 位 System32 装
`nvidia-smi.exe` / `nvml.dll`（实测 `SysWOW64` 下两个文件都不存在）。32 位下的实测结果：

| 检查 | 32 位结果 |
|---|---|
| `isfile(System32\nvidia-smi.exe)` | **False** |
| `isfile(Sysnative\nvidia-smi.exe)` | **True** |
| `shutil.which("nvidia-smi")` | **None** |
| `Sysnative\nvidia-smi.exe --query-gpu=name` | **ok → NVIDIA GeForce RTX 3090** |
| `ctypes.CDLL("nvml.dll")` | **OSError**（64 位 DLL 装不进 32 位进程） |

`C:\Windows\Sysnative` 是 32 位进程访问真 System32 的唯一虚拟别名。
用户截图里左侧 nvidia-smi 一切正常、右侧工具读不到，就是这个错位造成的。

### 修复（三层）

1. `server.py` 后端兼容：`_is_wow64()` / `_host_bits()` / `_smi_candidates()`（32 位时 Sysnative 排最前）；
   `_nvidia_smi_path()` **不再只信 `isfile`/`which`**（32 位会给假结果），改为真跑一次 `--query-gpu=name` 验证 + 进程内永久缓存；
   NVML 统一走 `_load_nvml()` 候选循环；`_gpu_list_impl` 的 `-L` 分支加空结果保护。
   `sysinfo()` 在 `free == 0` 时给出**专门警告**（原来会误报成「显存不够」）。
   `/api/env` 新增诊断字段 `pythonBits` / `pythonExe` / `wow64` / `smiPath` / `smiSource`。
   `main()` 启动横幅打印解释器位数 + 显卡名 + smi 路径。
2. `启动工具.bat` 重写：优先 64 位（`py -3.x-64` → 常见 64 位目录 → PATH python），每步用
   `-c "import sys;assert sys.maxsize//4294967296"` 校验位数；只有 32 位时才退 `py -3` 并打印警告。
3. `index.html`：「环境自检」新增 **Python 运行时**行（32 位时徽章显示「32 位」+ 解释 Sysnative 兜底），

### 顺手修掉：同端口双实例（SO_REUSEADDR）

排查中发现 8420 上**同时有两个 python.exe 在 LISTENING**（PID 9592/5008）。`http.server.HTTPServer`
默认 `allow_reuse_address = 1`，在 Windows 上等于允许第二个进程绑同一端口 → 浏览器随机命中其中之一，
页面数据自相矛盾（一窗口显存正常、另一窗口 0，刷新又变）。**这是此前"探测不稳定"假象的真正来源之一。**
修法：`_probe_tool()` + `_takeover_port()`，启动前探 `/api/env`，是自己就 POST `/api/shutdown` 接管并等端口释放。

### 本轮可复用的硬经验

- **`py -3` 不保证 64 位**！`py -3-64` 才强制 64 位。启动器必须做位数校验，别只看「有没有 Python」。
- **`.bat` 必须 CRLF**：LF-only 会让 cmd 解析偏移错位、把 `rem` 里的中文碎片当命令执行（`'ayedexpansion' 不是内部或外部命令`），**rc 仍为 0**，极隐蔽。
- **`.bat` 用 GBK + 无 BOM + 不写 `chcp`**（中文 Windows 控制台 CP936 原生），BOM+chcp 同时用也会偏移错位。
- 批处理里做位数校验用**无括号写法** `assert sys.maxsize//4294967296`，避免块内 `)` 计数问题。
- **沙箱内验证 .bat**：绝对路径 `C:\Windows\System32\cmd.exe` 会被拦（rc=1「命令语法不正确」），
  必须用 PATH 上的 `cmd`（`shutil.which("cmd")`）。
